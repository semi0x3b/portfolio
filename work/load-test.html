100만 DAU 대비 부하 대응

SK하이닉스 AI 해커톤 모집

1.3초에서 ;
25ms로 3,000 rps 10분 동안의 p95, 테스트 환경
기술
k6, PgBouncer, py-spy, Karpenter, OKE, Kong

문제

;

총상금 1억 원 규모인 SK하이닉스 AI 해커톤의 전국 공개 모집을 사내 SaaS로 받기로 했는데, 얼마나 버티는지 근거가 없었습니다. 재 보니 API 파드 하나가 공개 목록 조회 35 rps에서 한계였고, DB는 혼합 부하 200 rps에서 커넥션이 바닥나 요청이 실패했습니다.

한 일

;
  • 100만 DAU를 환산해 목표를 3,000 rps 10분, p95 500ms로 정했습니다. k6로 여덟 번 측정하면서 회차마다 병목을 하나씩 닫았는데, 요청마다 커넥션을 여는 세션과 트랜잭션 안의 메일 발송, 누수 트랜잭션의 커넥션 점유가 차례로 나왔습니다.
  • 서버를 늘리기 전에 요청 단가부터 낮췄습니다. 커넥션 예산식(pods × workers × (pool + overflow) ≤ max_connections)을 세워 PgBouncer를 넣었고, 프로파일러로 요청당 낭비 40%를 걷어냈습니다.
  • 운영 환경에서 부하를 올려 보니 포화 지점은 DB가 아니라 PgBouncer의 단일 스레드였습니다. 총 연결 수는 그대로 두고 4대 × 풀 45를 8대 × 풀 25로 다시 배치해 풀었습니다.
  • 클러스터 밖 첫 홉도 쟀습니다. 로드밸런서 대역폭(100 Mbps)은 평시 피크에 이미 차 있었고, 게이트웨이 요청 제한(IP당 분당 100회)은 같은 NAT 뒤 지원자 다섯 명이면 정상 사용자를 막는 값이었습니다. 두 값 모두 무중단으로 올렸습니다.

결과

;
  • 테스트 환경에서 3,000 rps 10분 동안 1,792,354건을 에러 없이 처리했습니다. p95는 1.3초에서 25ms로, DB CPU는 94%에서 7%로 내려갔습니다.
  • 모집 개시 사흘 전에 운영 환경에서 500→3,000 rps 램프를 통과했습니다(에러 0.001%, p95 2.5초).
  • 접수 8일 동안 방문 58,143명, 유효 지원자 7,460명을 받았습니다. 지원의 48%가 몰린 마감일 하루에 요청 935,219건이 들어왔고 5xx는 37건(0.004%)이었습니다.
  • 실제 피크는 58 rps여서 준비한 오토스케일은 한 번도 돌지 않았습니다. 이 작업으로 얻은 것은 증설 경로가 아니라, 상한을 알고 마감일을 맞았다는 점과 그 과정에서 닫은 병목들입니다.
