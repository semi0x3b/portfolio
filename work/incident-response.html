장애 자동 복구와 AI 원인 분석

외부 API가 멈춰도 버티는 서비스와 장애 분석 봇

전체 정지에서 ;
60건 모두 응답으로 외부 API가 응답하지 않을 때. 앞은 실제 장애(11분 정지), 뒤는 수정 후 동시 요청 60건으로 시험한 결과
기술
FastAPI, Kubernetes, Loki, Alertmanager, LLM
글과 코드
부검 봇 설계 글 log-autopsy 공개판

문제

;

외부 기관 API(HRD-Net)가 응답하지 않자 권한 서비스 전체가 11분 동안 멈췄습니다. 장애는 사용자 신고로 알았고, 그동안 쿠버네티스는 서비스를 재시작하지 않았습니다.

한 일

;
  • 응답 시간이 read timeout 30초의 배수로 쌓이는 것을 보고 원인을 찾았습니다. async def 핸들러가 동기 I/O를 실행하는데 워커가 하나뿐이라, 이벤트 루프 하나가 서비스 전체를 막고 있었습니다. await가 없는 핸들러 94건을 AST로 골라 sync로 바꾸고 threadpool에서 돌게 했습니다.
  • tcpSocket liveness는 커널이 소켓 연결을 대신 받아 주기 때문에 이벤트 루프가 멈춰도 통과합니다. 서비스 25종을 httpGet으로 바꾸고, 앱 프로세스를 직접 멈춰 45초 안에 재시작되는 것을 확인했습니다.
  • 장애 분석 봇을 만들었습니다. 규칙이 신호를 찾고 LLM은 해석만 맡습니다. 보내기 전에 인용한 문장이 원본 로그에 실제로 있는지 기계로 대조해, 근거가 없는 판정은 낮춰서 보냅니다. 봇에는 prod 변경 권한을 주지 않았고 복구는 쿠버네티스가 맡도록 나눴습니다.

결과

;
  • 외부 API가 멈춘 동안에도 동시 요청 60건이 모두 응답했습니다(QueuePool timeout 0건).
  • 25종에 적용한 뒤 probe 오탐으로 재시작된 경우는 0건입니다.
  • 과거 실제 장애 2건을 봇에 다시 돌리자 기록된 원인을 찾아냈습니다. 규칙 층을 LLM 앞에 둔 뒤로는 2주치 에러 알림 18건 중 9건이 LLM 호출 없이 판정됐습니다.
